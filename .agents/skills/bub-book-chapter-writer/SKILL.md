# Bub 设计解读书章节写作

用于为当前项目的《bub 框架设计解读书》撰写正式章节。目标不是介绍 API，也不是按目录树讲源码，而是围绕一个明确的设计问题，解释 Bub 为什么这样设计、解决了什么、放弃了什么、适合什么、不适合什么。

## 何时使用

当用户出现以下意图时使用：

- 明确要求“写这本书中的一个正式章节”
- 提供 `chapter_title`、`core_question`、`prerequisites`、`key_files`、`related_sources`、`comparison_targets` 之类的章节元信息
- 要求把某个架构主题扩写为成体系的书稿
- 要求按既定目录中的某一章继续写正文

不适用：

- 只是总结仓库功能
- 只是解释某个类/函数怎么用
- 只是生成 API 文档、README、教程式 quick start
- 只是按模块顺序做源码导读

## 写作前的硬规则

1. 先读源码，再写正文。
2. 章节必须围绕一个核心设计问题组织，不能把多个问题混成“杂项综述”。
3. 所有关键论断都要尽量落到真实源码、真实类型、真实调用链、真实测试或真实文档。
4. 如果某个判断没有源码直接证据，只能写成“这是一种推断”。
5. 如果源码与文档不一致，要直接指出，不要替文档圆场。
6. 如果某个实现明显是历史包袱，也要写明，不要包装成纯粹的设计美学。

## 输入解析

如果用户提供了章节元信息，优先按这些字段组织：

- 章节标题
- 本章核心问题
- 前置章节
- 相关源码入口
- 相关文档 / issues / PR / tests
- 如果需要比较的主流方案

如果用户给的是占位符而不是实际值：

- 先从 `docs/book/Bub 框架设计解读书：全书目录与阅读建议.md` 查找是否能唯一定位章节。
- 若仍无法唯一确定，再用一句简短问题向用户确认缺失信息。

## 写作流程

### 1. 先定位章节在全书中的角色

开写前先回答：

- 这一章在解释哪一个设计问题？
- 它依赖前面哪些章节？
- 它对后续章节有什么铺垫？

不要把章节写成孤立文章。

### 2. 建立源码证据面

至少阅读：

- 本章给出的关键源码入口
- 与该问题直接相关的测试
- 如有必要，阅读目录文档 `docs/book/Bub 框架设计解读书：全书目录与阅读建议.md`
- 如已存在相邻章节，也读一下已写章节，避免重复定义概念

需要时补充：

- `README.md`
- `docs/features.md`
- `docs/extension-guide.md`
- `docs/read-v2/`

### 3. 抽出“设计问题”而不是“代码清单”

正文必须回答：

- 这个设计在解决什么问题
- 为什么不是更直觉的另一种做法
- 它依赖哪些前提
- 它把复杂度放到了哪里
- 它不适合哪些情况

如果写完后只能回答“有哪些模块/函数”，说明写偏了。

### 4. 组织章节结构

章节默认按下面的骨架展开，必要时可微调，但不要删掉关键段落：

1. 章节开头：定位 / 前置依赖 / 适用场景
2. 核心设计问题
3. 这个问题为什么存在
4. 真实实现的边界与结构
5. 关键数据流 / 控制流 / 状态流
6. 与主流做法相比，这里的选择是什么
7. 适用边界与失败模式
8. 取舍分析
9. 版本演化说明

### 5. 输出格式约束

开头固定写：

```markdown
> 定位：
> 前置依赖：
> 适用场景：
```

并且：

- 在正文前 10% 内明确抛出“本章的核心设计问题”
- 章节结尾固定包含：
  - `取舍分析`
  - `得到了什么`
  - `放弃了什么`
  - `版本演化说明`

## 内容要求

### 必须有的内容

- 真实模块、真实类型、真实调用链
- 必要时的 Mermaid 图、表格、关键代码片段或伪代码
- 至少一次明确的方案对比
- 如果这一章涉及调用链，要把链路写清楚
- 如果有二次开发价值，要明确指出“改这里会影响什么”

### 明确禁止的写法

- 不要按函数顺序讲代码
- 不要把章节写成 feature 列表
- 不要空泛夸赞“灵活”“强大”“优雅”
- 不要把产品层决定误写成 runtime 核心
- 不要假装理解作者意图

## 风格要求

- 中文
- 工程化、冷静、清晰
- 判断明确
- 不营销
- 不说套话
- 不回避成本、失败模式和边界

章节标题要像技术书章节，不像 issue 标题。

## 可读性增强要求

在保持“基于源码、判断明确、不回避代价”的前提下，正文风格需要比纯架构分析更易读。默认采用下面这些写法：

### 1. 先讲人话，再讲抽象

- 每章开头在抛出核心设计问题后，尽快用 2-4 句话说明“这件事到底在解决什么实际困扰”。
- 对抽象概念，优先先给出一个具体场景或小例子，再进入源码和术语。
- 能用“如果你在改 X，会先撞到什么问题”说明的，不要直接进入抽象定义。

### 2. 过渡要自然，不要跳跃

- 段落之间要明确交代“为什么接下来讲这个”，避免从问题直接跳到代码细节。
- 每个大节开头先用一句过渡句，说明它和上一节的关系。
- 从设计问题切到源码实现时，先说“这个判断在源码里落在哪几处”，再展开。

### 3. 默认加入小例子

- 只要章节允许，至少加入 1-2 个简短例子。
- 例子优先选工程里的真实情境，例如：
  - “一条 Telegram 消息进来以后会怎样”
  - “一个插件想覆盖 builtin prompt 时会发生什么”
  - “如果没有 model 输出，框架会怎么兜底”
- 例子必须服务于理解设计，不要写成教程步骤。

### 4. 结论前置，源码跟上

- 每个核心小节先给一句明确判断，再给源码证据。
- 避免一上来就是大段代码或大量文件名；先告诉读者“这段代码为什么值得看”。
- 代码片段只保留支撑当前判断所需的最小部分。

### 5. 控制抽象密度

- 长段优先拆短，连续抽象名词过多时要穿插解释句。
- 避免连续多段都在谈“语义、边界、策略、机制”这类高抽象词而没有具体落点。
- 如果一个概念在前文没有稳定定义，本章首次出现时用一句话解释它在当前上下文中的具体含义。

### 6. 保持工程判断，但不要写得像审判书

- 可以明确指出问题、代价和历史包袱，但语气要平实。
- 尽量少用连续的强判断句堆砌压迫感，适当增加“换句话说”“这意味着”“可以把它理解成”之类的解释性连接。
- 允许用有限的类比帮助理解，但类比必须简短，并且很快落回源码事实。

### 7. 对已有章节的默认修正方向

如果继续补写后续章节，默认采用以下改进：

- 开头更快落到实际问题，不在前两屏堆太多抽象判断。
- 每节增加“先解释，再落代码”的层次。
- 更少使用过长句和连续并列判断。
- 在适合的位置加入“小例子”或“假设场景”帮助读者形成直觉。

## 对比策略

如果章节涉及设计取舍，至少选择一个对比对象：

- Agent-centric 设计
- Graph / DAG / workflow-centric 设计
- 强类型 runtime contract
- 单宿主 bot 框架
- API-first 推理网关

对比不是为了证明 Bub 更好，而是为了说明 Bub 把复杂度放在了哪里。

## 写作完成后的自检清单

- [ ] 开头是否包含 `定位 / 前置依赖 / 适用场景`
- [ ] 前 10% 是否已经明确提出核心设计问题
- [ ] 是否基于真实源码而不是凭印象
- [ ] 是否解释了“为什么不是另一种更直觉的做法”
- [ ] 是否写清楚依赖前提、复杂度转移和不适用边界
- [ ] 是否至少有一次真实的方案对比
- [ ] 是否避免按模块顺序讲代码
- [ ] 是否在结尾写了 `取舍分析 / 得到了什么 / 放弃了什么 / 版本演化说明`
- [ ] 是否有足够自然的过渡，而不是段落间硬切换
- [ ] 是否至少有一个帮助理解的具体例子或场景
- [ ] 是否做到“先讲人话，再落源码”

## 项目内建议落点

如果用户要求将章节保存到仓库中：

- 默认保存到 `docs/book/`
- 文件名格式固定为 `第XX章-章节标题.md`，其中 `XX` 是按目录 `docs/book/Bub 框架设计解读书：全书目录与阅读建议.md` 对应的两位数字章节号（补零，例如第 1 章是 `01`，第 12 章是 `12`）
- 正文一级标题固定为 `# 第 N 章 章节标题`，其中 `N` 不补零，与目录表述保持一致（例如 `# 第 1 章 Bub 在解决什么问题`）
- 如果目录中未包含该章节，先停下来跟用户确认章节编号，不要自行猜号

如果用户只要求输出正文而未要求落盘，则直接返回章节内容，不额外创建文件。
